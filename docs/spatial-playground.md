# Spatial playground

This experiment explores a desktop as a place to arrange icons, folders, and windows. It runs entirely in the browser, using React local state and CSS Modules. The current interaction has no server state or routing requirement.

## Canvas and coordinates

A native scroll container fills the viewport and hides its scrollbars. Its world starts ten screens wide and ten screens tall. At creation, one screen is the browser’s initial viewport size, with a minimum of 960 × 720 pixels. Arranging windows can expand the world to fit the result. The saved world keeps its dimensions across reloads.

The home viewport starts at 4.5 screen widths and heights into that world. Desktop items and windows use absolute world coordinates, so ordinary scroll movement also moves the dotted wallpaper. At desktop widths, fixed controls sit above the scrolling viewport in four corners: notifications at top left, device status at top right, canvas tools at bottom left, and the app launcher at bottom right. Device status combines the clock and three icon buttons in one compact glass row. At 760 pixels or less, the top corners join into one bar and the bottom corners join into another, preserving their left-to-right roles.

The minimap translates pointer positions into world coordinates. Grabbing its visible-area rectangle preserves the pointer’s offset within the viewport; pressing elsewhere centers the viewport there. Pointer capture keeps navigation continuous outside the map until release, and the native scroll container clamps travel at the world edges. The Overview panel contains the map without a window count, dragging hint, or Home button; the Home key still returns to the starting viewport. Icon-only zoom-out and zoom-in buttons sit beside its heading. They are presentational placeholders and do not change the map scale or canvas viewport.

Dragging a window’s title bar combines pointer movement with changes in scroll position. This keeps a grabbed window under the pointer while edge scrolling carries it farther across the world. Shell-owned windows join a glass title bar and opaque content in one frame, with a 44-pixel header increasing to 50 pixels for coarse pointers. External app previews use their own Realistic frame styles while retaining the same window interactions. The body scrolls in the remaining space. Eight resize handles constrain windows to the world bounds and a minimum size of 280 × 200 pixels.

Double-clicking a window header toggles ordinary maximization, using the current viewport with clearance for the shell controls while retaining previous bounds for restore. The shared `windowClearance` uses 24-pixel side margins, 96 pixels above, and 96 below at desktop widths; at 760 pixels or less, these become 12, 78, and 78 pixels. Revealing a maximized window uses the same offsets; ordinary windows are centered with the top and side clearances as minimums. The same minimum window dimensions still apply on small viewports.

The header’s maximize button instead enters a focused view. The window fills the viewport while keeping its title bar and app content; shell controls hide and canvas navigation stops. The app’s own scrolling and controls remain usable. Ordinary maximized bounds are retained underneath this temporary presentation, preserving the original restore bounds.

Moving within 72 pixels of both edges of any viewport corner reveals all shell controls immediately. They remain visible while the pointer is over shell controls, while keyboard focus is in the shell, or while a shell panel or tool menu is open. Otherwise they hide after a 450-millisecond grace period. A touch near a corner reveals them for 2.5 seconds; taps on window header buttons retain their normal action without revealing the shell. Choosing a different window or launching an app leaves focused view, with the previous window remaining ordinarily maximized. Selecting the same window keeps it focused. Pressing the focus control again or double-clicking the header also returns to ordinary maximization; a subsequent header double-click restores the original window size. Focused view is temporary and is not saved with the workspace.

Window selection supports a rectangle or freeform lasso in world coordinates. The viewport captures selection input before window controls, then highlights windows intersecting the selected area. Rectangle select uses the bounds between the start and current pointer positions. Freeform lasso follows the drawn path and closes it by connecting the last point to the first; windows intersecting that polygon are selected. Taps and straight strokes do not enclose a selectable area. The selected IDs remain after release until cleared. When more than one window is selected, dragging any selected window’s title bar moves the group while preserving selection; starting outside the selected group draws a new selection. Arrangement operates on every window independently of either selection. Space-drag and middle-button dragging temporarily pan in any canvas mode.

Selecting one or more windows exposes a floating **Gather similar windows** button beside their combined bounds. Its two overlapping rectangles and tooltip identify the action without adding a selection count. The control follows window movement and viewport travel, stays within the visible work area, and hides when every selected window is offscreen or during focused view, canvas search, or window switching. When neither side has room, it moves inward below the title bar to keep window controls reachable. It sits outside the scroll container so using it does not start another selection or pan gesture.

Gathering is an AI feature preview. Until AI is enabled in Settings, the button remains visible but unavailable, with a tooltip pointing to **Settings → AI**. After opt-in, pressing it starts a one-second shimmer, then brings other windows from the selected application or applications into the current viewport near the selection. Selected and unrelated windows keep their geometry. Oversized matches fit within the available area, and crowded matches cascade. The result updates ordinary workspace geometry and is saved with the layout.

`GatherWindows` owns the delay and shimmer; `gather-windows.ts` chooses and places the matching windows. A selection change, disabling AI, or unmounting the control for search, window switching, or focused view cancels pending work. Reduced motion uses a static busy highlight during the same delay. Matching uses app identity only. No model is downloaded, no window contents are analyzed, and no AI service is called.

## Desktop items

Projects and Pictures folders, a Notes.txt document, and a shortcut for every app in `APP_CATALOG` start near the home viewport. App shortcuts are permanent and movable; the user can arrange them alongside files and folders, but cannot remove an app's desktop entry. These are simulated entry points into app previews. Desktop items occupy a separate layer below all windows, so selecting or moving an item never raises it over a window. This layer leaves room for future desktop widgets; no widgets are implemented.

Pan mode drags the canvas even when the drag starts on an item. The cursor is the default tool and selects desktop items. Dragging the background draws a rectangle in world coordinates and selects intersecting items without selecting windows. Clicking an item selects it; Shift, Ctrl, or ⌘ toggles individual items or adds a rectangle’s matches to the selection. Space selects a focused item. Dragging a selected item moves the selected group together, keeping it within the world bounds. Double-click or Enter on a focused item opens its associated simulated app preview without changing the canvas tool. Window and desktop-item selections have separate IDs. Desktop selection is shown through item highlights and the dragged rectangle, without a text hint or count.

Item positions persist with the workspace and remain independent of window geometry and stacking. Arrange only moves windows. Loading a workspace preserves existing desktop items and moved app shortcuts, removes duplicate shortcuts for an app, and adds any missing catalog shortcuts near home. A workspace without an item collection also receives the starter files and folders. Windows and edited scratchpad content remain intact.

## Canvas search

Search is a primary canvas tool alongside desktop selection and Pan. Choosing it leaves the canvas in place until a background click opens search near that client-space point. The / shortcut selects Search and opens it near the upper center of the viewport. Starting search exits focused view, closes other panels, clears selections, and holds the viewport at its current scroll position.

The field stays near the clicked point, clamped to leave the shell controls available. Results use the space below a field in the upper half of the viewport, or above one in the lower half. With an empty query, all desktop items gather into view and windows move outside the viewport. Typing filters item titles and kinds, plus window titles and their app names. Matching is case-insensitive and requires every space-separated query term to appear. For example, Notes can match a shortcut, Notes.txt, and open Notes windows, while `folder` finds desktop folders.

`getCanvasSearchLayout` computes presentation coordinates and scales from the current workspace, viewport, anchor, and query. Matching items and actual window surfaces fit into a result grid; nonmatching objects move beyond a viewport edge. Windows keep their content and chrome, with inner controls inactive while they act as search results. The original workspace coordinates, sizes, and stacking remain unchanged. Closing search removes these temporary placements, so panning, arrangement, and persistence continue to use the workspace's ordinary geometry.

Results place desktop items first, then matching windows in front-to-back order. Up and Down change the selected result, wrapping at either end; Left and Right retain normal text-cursor behavior. Enter or clicking a result closes search, then opens the item's associated preview or focuses and centers the existing window. Escape, the field's close button, empty-canvas input, or another shell or tool action also closes search. Dismissing it preserves the Search tool, ready for another background click. The field has no result count or instruction footer; a query without matches displays **No matches**.

Canvas search uses the playground's local item and window metadata. It doesn't inspect app contents or the host filesystem. The regular launcher search and dock continue to provide their existing routes to apps and window instances.

## Arranging windows

Arrange gathers all open windows near the current viewport, including offscreen and unselected windows. It first restores the bounds of maximized windows and removes their maximize state. Each window then keeps its width and height.

The grid uses `ceil(sqrt(windowCount))` columns. Each cell uses the largest window width and height, with 24 pixels between cells, so windows of different sizes do not overlap. Placement begins 24 pixels to the right and 96 pixels below the current viewport’s world origin. World bounds grow when necessary to contain the grid.

Placement order follows the windows’ previous vertical positions, then horizontal positions, with the window ID breaking ties; maximized windows use their restored positions for this ordering. The workspace’s window array retains its stacking order. Arranged geometry and any expanded world bounds use the existing workspace persistence.

Running Arrange leaves focused view, closes open panels, and clears selection while preserving the chosen canvas tool. The button is disabled when there are no windows, and the arrangement calculation leaves an empty workspace unchanged.

## Canvas tools and launcher

At desktop widths, the fixed canvas dock at the bottom left contains separate dropdowns for background tools and window selection, followed by a divider and Map and Arrange. The first dropdown’s top-right indicator exposes **Select desktop items** (V), **Pan canvas** (H), and **Search canvas** (/); its icon reflects the remembered background tool. The second dropdown chooses **Rectangle select** (R) or **Freeform lasso** (L), with a square or lasso icon and its own top-right indicator. Pressing an inactive dropdown tool activates its remembered choice without opening the menu; pressing it again opens its choices. Up or Down on a focused tool opens its menu directly. Desktop-item selection always uses a rectangle, independent of the chosen window-selection shape. Canvas-tool hints appear on hover or focus and dismiss after 2.5 seconds, on pointer exit or blur, or when the control is activated. Arrange runs immediately; its hint identifies the action and A shortcut. Apps creates preview windows, and the Home key returns to the starting viewport.

Desktop corner surfaces are 54 pixels high and sit 24 pixels from the viewport edges. At 760 pixels or less, two shared 54-pixel bars sit 12 pixels from the top, bottom, and side edges. The bottom bar contains one canvas-tool selector, the horizontally scrollable app strip, and the Apps launcher. The selector opens a single flat menu containing desktop-item selection, pan, search, rectangle select, freeform lasso, Overview, and Arrange windows, without submenus. Choosing a tool or action closes the menu.

The notification trigger pairs a bell with a single-line unread status. Its contents remain left-aligned at their natural width, preserving the full label on narrow screens. The clock and network, sound, and battery buttons occupy the right side; the device-icon strip scrolls horizontally when space is limited. Enabling the battery percentage widens its button. The full date and simulated device values appear in hover titles and expanded panels.

Desktop top panels open 12 pixels below their corner surfaces; Map, launcher, and window picker panels sit 90 pixels above the viewport bottom. On narrow screens, top panels start 78 pixels from the viewport top, and bottom panels sit 78 pixels above the viewport bottom. Their maximum height is the viewport height minus 156 pixels, with internal scrolling keeping both bars reachable.

One continuous glass dock at the bottom right contains preset Browser, Files, and Notes favorites, other apps with open windows, and Apps. Individual icon buttons have no separate resting bubbles. Running favorites reuse their existing icon button. Each running app shows one dot per window below its icon, capped at three dots; its hover title and accessible name retain the exact count. The app containing the active window is marked. Apps opens the launcher, where an Apps/Draw toggle in the command bar selects browsing or the gesture pad.

The app strip scrolls horizontally when crowded, including within the shared mobile bottom bar. On mobile, its icons stay aligned to the right beside Apps when they fit, and the strip shrinks to scroll when needed. The app icons keep their 44-pixel targets inside the 54-pixel surface, and Apps remains beside them. Panels reserve space for that bar. The launcher panel sits above the dock and stays within the viewport. Canvas tools and dock apps use icon-only buttons with accessible names; desktop toolbar hints and dock hover titles identify their actions. Their targets remain at least 44 × 44 pixels across input types. Names remain visible in the app gallery and window picker.

`App` owns the active canvas mode, selection, and panel visibility, including notifications, device popovers, and the window picker. Opening a panel dismisses panels from the other control groups. Window and desktop-item selection use drawn outlines and highlights for feedback, without persistent selection instructions or counts. Pointer input outside the launcher or device popover closes it. Escape closes open panels; on the canvas, it clears selection and cancels an active selection gesture without changing tools. Arranging windows, launching apps, and revealing existing windows also preserve the chosen tool.

Single-letter shortcuts and / are suspended while the launcher is open or a text input is active. The launcher filters a local catalog by app name and description, supports a four-column app gallery and a single-column list, and presents search results as a list. Within the launcher, only search results show a count. Arrow keys navigate apps and Enter launches the selection. Up and Down move four entries in the gallery and one entry in list and search views. Fine-pointer devices focus search when the Apps view opens; coarse-pointer devices avoid automatically opening the software keyboard.

Selecting a running app opens a popover listing its window instances, even when only one exists. Its header contains the app name and close button. Each row shows a preview, title, and right-hand reorder handle, with a highlighted background for the active window; accessible names retain instance numbers and active state. Selecting an instance raises and focuses that window, then scrolls it into view using the shared window clearance and clamping at the world edges. The list groups the original scratchpad with Notes and includes Workspace and generic Windows groups so every workspace window remains reachable. Catalog apps offer **New window** to create another instance; a favorite with no windows launches directly. Arrow Down on a running app’s dock button opens the picker and focuses its first window. Escape closes the picker and returns focus to that button.

Drag a row’s handle with a pointer or touch to preview a different order; release saves the change, while cancellation restores the previous order. Up and Down on a focused handle move its window one place. Reordering changes only the picker order, leaving canvas positions, stacking, and the active window unchanged. Each window’s optional `dockOrder` stores this order in the existing workspace state. New instances follow the ordered windows; closing an instance removes its row normally.

Launching from a non-running favorite, **New window**, an app result, or the gesture pad creates an ordinary movable, resizable preview window with the catalog app’s title, icon, and description. Each uses the same launch action in `App`. There is no operating-system launch integration, favorite-editing UI, or separate running-app persistence; the dock derives its groups from workspace windows.

## Keyboard window switcher

Hold Ctrl and press 1 to gather every open window into a temporary grid within the viewport, including offscreen windows and multiple instances of the same app. Ctrl+1 advances and Ctrl+Shift+1 moves backward, wrapping at either end. Opening captures the current window order from front to back, with the active window first, so cycling starts from the most recently focused windows and remains stable during the interaction.

The existing window surfaces move and scale for this presentation, retaining their content and chrome. Desktop items move out of the way. The chosen window receives an outline and a single title centered underneath it. Cycling changes that selection without focusing a window, changing workspace geometry or stacking, or moving the viewport. Inner window controls are inactive during the choice. The presentation uses temporary coordinates, like canvas search, and never writes them into workspace storage.

Releasing Ctrl commits the highlighted window, restoring the ordinary layout and centering the viewport on it with world-edge clamping. Enter or clicking a window also commits. Switching to another window leaves focused view using the existing ordinary maximization behavior. Escape, clicking empty space, or losing browser focus cancels without committing. Cancellation restores the original layout and any previous focused view; keyboard focus returns when cancellation happens within the page. The browser or operating system can reserve keyboard combinations; this prototype handles Ctrl+1 only when those key events reach the page.

Search and switcher commits share the movement in `preview-motion.ts`. Before closing the preview, it measures the existing window elements in viewport coordinates. After restoring workspace geometry and instantly recentering the canvas, it measures their final bounds and animates from the previous visible rectangles to those bounds. This measure-before-and-after technique, often called FLIP, gives the chosen window one direct movement instead of a return to its saved position followed by a second movement during scrolling. Other windows move continuously toward their restored positions; distant offscreen paths stop at the viewport edge to avoid racing across it. The animation uses the same elements, without clones or fading out and reappearing. Reduced-motion preferences skip it and show the final view immediately.

## Notifications

Notifications open from the top-left bell or with N. The trigger shows an accented ringing bell and an unread count, such as **3 new**, while items are unread, or a subdued bell and **All clear** otherwise. This full label remains visible on narrow screens. App actions ask `App` to reveal a matching window, including the original scratchpad for Notes. This uses the same raise, focus, and scroll action as the running-window picker, with immediate scrolling when reduced motion is preferred. If no matching window exists, it creates an app preview near the current viewport.

`NotificationInbox` owns three initial sample notifications, unread flags, dismissals, and an optional toast. Opening the inbox does not mark items read. Following an item’s action marks it read; **Mark all read** changes all unread flags, while a row’s dismiss button removes that item. Pointer input outside the inbox closes it. Escape closes the inbox and any active toast.

The gesture pad’s cog asks `App` to close the launcher and open notifications. The `NotificationInbox` ref exposes `showGestureSettings()`, which moves a single **Customize gestures** item to the top, marks it unread, and clears any toast. Its `gestures` target reopens Draw in editing mode through `App`. Repeating the request does not create duplicate items.

The separate prototype footer contains a quiet **Preview notification** button. It cycles through Notes, Files, and Browser examples, prepends a new unread item, closes the inbox, and shows a toast for six seconds. Toast actions use the same window navigation as inbox actions. Outside pointer input dismisses the toast, and opening another corner panel suppresses it so controls remain visible on narrow screens. Closing or timing out the toast leaves the item in the inbox. All notification content and relative timestamps are simulated, with no external event source.

## Gesture shortcuts

The Draw view contains a dedicated pad so drawing does not compete with desktop panning or window selection. Its default view contains the pad and customization cog, without an app selector, saved-shortcut list, or manual launch action. A recognized stroke launches its assigned app and closes the launcher. Unrecognized marks remain available to retry. Settings has a separate **Gestures** category for viewing and managing assignments, initially populated with Browser, Terminal, and Notes examples.

The pad’s cog opens the notification flow described above. Following **Customize gestures** opens the launcher editor, where **Open this app** uses the searchable app picker to select an assignment target. **Save shortcut** replaces that app’s mark while retaining other assignments and returns to preview mode. This launcher flow retains **Cancel**, which clears the unsaved stroke and returns without writing storage.

In Settings, **Add gesture** sits beside the Gestures heading and opens the same pad in editor mode. Choose an app, draw one continuous stroke, and save to add its assignment. The app picker shows icons and names and supports searching the catalog. Each saved row pairs a stroke preview with the app’s icon and name and offers editing and removal. Editing starts with the saved mark; **Retry** clears the pad for a replacement. Changing the target app moves the assignment and replaces any existing mark for that destination, keeping one mark per app. The editor’s back control discards the draft and returns to the list. Moving between the list and editor returns the content pane to the top. Removing all assignments leaves an empty list that remains empty after reload.

`App` owns the saved assignments and passes them to each Settings window. Changes made in Settings or the launcher editor are immediately reflected in the other views. Draft strokes and the open editor belong to their current component and are not saved until **Save shortcut** is used.

The app picker uses [React Aria’s ComboBox](https://react-aria.adobe.com/ComboBox) above the drawing pad. Its text input filters app names and descriptions in a popup list, with an icon and name for each choice and a check on the current selection. React Aria owns list navigation, selection, focus, and popup dismissal; app-specific CSS Modules supply the styling. Changing the selected app preserves the drawn mark. The picker is shared by Settings and the launcher editor.

The picker popup portals into the themed desktop root, escaping window scrolling boundaries while retaining the selected accent, color mode, and app artwork. Its launcher containment marker keeps selecting a popup option from triggering the launcher's outside-pointer dismissal.

The pad records a single pointer stroke in a 440 × 190 coordinate space, scaled to the displayed surface. Pointer capture keeps the stroke active outside the pad, with points clamped to its bounds. A saved shortcut contains its app ID and up to 2,048 points. Each app has at most one saved mark.

The normal pad uses the local $P geometric template matcher to compare a completed stroke with saved assignments. Matching preserves orientation while allowing changes in position, size, stroke order, and direction. Weak or ambiguous matches show **No match found** and leave the mark available to retry; taps and canceled pointers never launch. Editing mode never auto-launches. Saving requires a mark with at least two points and no active pointer stroke; an existing mark can be reassigned without redrawing it.

## Settings

The Settings app has sidebar navigation for **Appearance**, **Displays**, **Background**, **Gestures**, **AI**, and **System**, opening on Appearance. Its 160-pixel sidebar collapses behind a category toggle when the Settings content container is narrower than 560 pixels. Choosing a category closes the compact navigation and returns the content pane to its top. Navigation belongs to each Settings window; saved preferences and gesture assignments are shared across them. New Settings windows open up to 680 pixels wide, constrained by the viewport and ordinary minimum window size; existing saved window sizes remain intact.

**Background** accepts a local photo and applies it beneath desktop items and windows. **Repeat with canvas** tiles the image at its native size on the scrolling world. **Stretch**, **Contain**, and **Cover** instead use a centered, viewport-sized background layer that stays still while the canvas moves. Stretch scales both axes independently, Contain preserves the whole image with the current theme’s field color around it, and Cover preserves proportions while cropping to fill the viewport. Cover is the initial fit; replacing a photo retains the existing fit. **Use default background** restores the accent-colored dot pattern without changing the other appearance preferences.

**Appearance** offers a global **Light** or **Dark** mode. Without a saved choice, the initial mode follows the operating system's `prefers-color-scheme` preference. Selecting a mode immediately updates the canvas, shell, expanded panels, and window surfaces and text. Realistic windows use their own dark palettes and keep their app-specific chrome designs; the already-dark Terminal, Music, and Photos previews remain dark. The shared choice belongs to `App`, so all open Settings windows stay in sync. The root `data-color-mode` attribute selects the matching CSS palette and native `color-scheme`.

The same view offers six allowed accent choices: Orange, Rose, Violet, Blue, Teal, and Olive. Orange is the default. The selection belongs to `App`, so every Settings window reflects the same current choice. Changing it updates the root app’s `--accent-base` property and `data-accent` attribute. Shared CSS properties derive the displayed accent and environment’s palette from that base color and the selected Light or Dark mode. Orange retains its original values in Light mode, while each accent has a lighter Dark-mode color for contrast. Canvas tints, controls, window states, notifications, and gesture strokes use that shared palette. There are no per-component overrides or custom color inputs.

App previews always use Realistic styling; **Appearance** contains only color mode and accent controls. The root uses `data-presentation="realistic"`, giving external app previews independent identities with varied icon silhouettes and backgrounds, frame shapes, title bars, and interior colors. The shell keeps its four-corner layout and shared accent cues; Workspace and Settings retain glass chrome and opaque content. This is a visual approximation of a mixed Linux desktop, not an integration with host applications or a reproduction of particular toolkits.

Accent and Light/Dark changes apply immediately to existing windows and their entries in the dock, launcher, and notifications. They do not replace the workspace or alter window geometry, stacking, dock ordering, or scratchpad content. The accent and Light/Dark mode remain separate global settings: shared controls and state cues use the accent, while each Realistic app keeps its own light/dark surface palette and chrome design. App icon artwork and photo backgrounds keep their original colors in either mode. There are no individual app theme controls.

**Gestures** presents the saved app assignments and the add, edit, and remove flow described above. These controls edit the local templates used by the gesture launcher.

**AI** includes a **Features** subheading with two collapsed entries. **On-device AI** comes first and describes the intended local processing, without sending device information off the device. **Gather similar windows** follows, explaining how selected windows would provide context for bringing related windows into the current viewport. AI is off by default. Download information sits below its toggle row; opting in starts a simulated 3 GB model download lasting about four seconds. Turning the toggle off during the download cancels it immediately. Completion enables the gathering preview across all Settings windows.

Turning off enabled AI first requests confirmation, explaining that the 3 GB local model will be deleted and must be downloaded again to re-enable AI. Canceling retains the enabled state; confirming disables it. This remains a presentation of the intended model lifecycle: the playground stores no model file, sends no device information, and performs no download or AI processing. Closing Settings or changing categories leaves a simulated download running for the session, while reloading before completion leaves AI disabled.

**Displays** previews a two-monitor setup. Drag either numbered monitor to arrange it around the other; releasing snaps it to the nearest shared edge so the pair stays connected without overlap. Selecting a monitor reveals its own mock resolution, scale, and refresh-rate controls. These controls change only the preview’s state, with no connection to the host’s monitor configuration or the desktop canvas.

The arrangement uses an 800 × 450 coordinate space in a responsive preview capped at 400 × 225 CSS pixels. During a drag, the other monitor stays fixed and the dragged tile stays within the board. On release, snapping considers all four sides and preserves at least 24 logical pixels of shared edge. Nearby starts, centers, and ends align within a 12-pixel threshold. The pair then recenters as a group, keeping its relative arrangement while leaving equal margins around its combined bounds. Pointer capture supports mouse, pen, and touch dragging beyond a tile; cancellation restores the original layout. Arrow keys place the focused monitor on another side and recenter the pair in the same way.

Each Settings window owns its mock layout and per-monitor values, retaining them across category changes until that window closes or the page reloads. They are not shared with other Settings windows or persisted. Resolution and scale are form values only; they do not resize the monitor tiles or the desktop. The selected monitor and active drag belong to the Displays view.

**System** contains the **System tray** section and its **Show battery percentage** toggle, off by default. `App` shares the preference across Settings windows and passes it to the system row, where it displays **87%** beside the battery icon. The battery value remains simulated, and its popover shows the percentage regardless of this preference.

## Saved state

Photo backgrounds are stored in IndexedDB database `hearthspace-background-v1`, in the `background` store’s `photo` record. The record holds the original image Blob, filename, and allowed fit value, independently of the workspace and other appearance settings. The image is decoded before use and is not sent to a server. Resetting deletes this record. If saving or deleting fails, the current session still shows the selected background and Settings explains that the change could not be saved. An unavailable or unreadable saved photo falls back to the default dots.

The workspace is stored in `localStorage` under `hearthspace-playground-v1`. It contains world dimensions, home coordinates, desktop items and their positions, window geometry and stacking, optional dock list ordering, app IDs for launched preview windows, and the scratchpad note. Loading validates the stored shape and constrains window and desktop-item bounds. Desktop items require unique IDs, a supported kind, and a known preview app. Workspaces without an item collection receive the starter items. Every loaded workspace gains any missing catalog app shortcuts; a saved empty collection therefore receives app shortcuts, while files and folders remain absent. Existing app-shortcut positions are preserved and duplicate app shortcuts are removed. Maximized windows return to their saved restore bounds on reload. The visual refresh renames the original demo titles and converts its generic starter window into a Files preview. Only the exact original sample note is replaced; edited notes and saved geometry remain intact.

Gesture shortcuts are stored separately under `hearthspace-gesture-shortcuts-v1`, preserving previously saved assignments. Loading accepts known catalog app IDs, unique assignments, and finite points within the pad bounds. Missing or invalid storage uses the default examples; a saved empty array stays empty. Invalid entries are filtered when valid assignments remain. `App` retains changes for the current session if storage fails, including across closed and reopened Settings or launcher editors; those changes will not survive a reload.

The color mode is stored separately under `hearthspace-color-mode-v1`. Only `light` and `dark` are accepted. Missing, invalid, or unavailable storage uses the operating system's `prefers-color-scheme` preference on load; an explicit choice takes precedence on later loads. Changes remain usable in the current session if saving fails. The mode is independent of the accent, workspace, and photo background.

The accent is stored separately under `hearthspace-accent-v1` as an allowed theme ID. Loading rejects unsupported values and falls back to Orange when storage is absent or unavailable. Changes remain usable in the current session if saving fails. This setting does not alter the workspace or gesture storage.

App appearance is fixed to Realistic and has no saved preference. Values left under the legacy `hearthspace-app-presentation-v1` key are ignored. Existing workspace geometry, content, and other preferences remain intact.

The selected canvas tool is stored under `hearthspace-canvas-tool-v1`. Loading accepts `cursor`, `pan`, `search`, or `select`; the earlier `lasso` value migrates to `select`. Missing, invalid, or unavailable storage defaults to the cursor. Explicit tool changes remain active through Escape, arrangement, app launches, and window navigation. Temporary panning does not change the saved tool. Remembering Search restores the tool on reload, with its field closed.

The window-selection shape is stored separately under `hearthspace-window-selection-v1` as `rectangle` or `freeform`. Missing, invalid, or unavailable storage defaults to rectangle. Changing the shape activates window selection; choosing another tool leaves the shape remembered for later use and reloads.

Battery-percentage visibility is stored under `hearthspace-battery-percentage-v1`. Only the literal string `true` enables it; missing, invalid, or unavailable storage defaults to off. The preference applies immediately and remains usable in the current session if saving fails.

AI opt-in is stored under `hearthspace-ai-enabled-v1`. Only the literal string `true` enables it; missing, invalid, or unavailable storage defaults to off. Confirming opt-out or canceling an active download saves `false` immediately. Opting in saves `true` only after the simulated download completes, so an interrupted download does not enable the feature on reload. Download progress is temporary and no model file is stored. The shared session remains usable when preference storage fails.

Viewport travel, selection, open panels, temporary window-switcher layouts, search text and result arrangements, list/grid choice, notifications, and simulated device-control values remain temporary. Search and switching never write their presentation coordinates to workspace storage. Notification read/dismissal state and preview items reset to the initial samples on reload. If storage is unavailable, the current desktop session remains usable without persistence.
